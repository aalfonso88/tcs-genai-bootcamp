> objetivo

- te pediré que me escribas un prompt que pueda ser usado como inicio de un proyecto a ser elaborado usando vibe coding.
    
- El enfoque será crear inicialmente un prompt que describa en alto nivel el objetivo de la aplicación usando google AI studio. Dentro de estas especificaciones le diremos que utilice python/fastapi y reactjs aunque es posible agregar las herramientas complementarias que considere utiles y necesarias (servidores web, librerías como vite, axios, tailwind, etc).
    
- El enfoque será iterativo, es decir, la primera versión será minimalista, con las funcionalidades básicas y suficientes para hacer las primeras pruebas, y eventualmente incorporar nuevas o hacer cambios. No hace falta en la primera versión incluir tests de ningún tipo.

 > descripción de la app

una app para gestionar reservas en una casa de masajes.

- No tendrá inicialmente autenticación.
    
- Su finalidad es permitir que los usuarios agenden una sesión de masajes.
    
- La sesión puede ser una de tres tipos: RELAJANTE, DESCONTRACTURANTE o HíBRIDA
    
- El usuario podrá agendar su masaje usando el saldo de su cuponera o compando individualmente el masaje.
    
- Se asume que el usuario inicialmente posee una cuponera con 8 masajes disponibles. El saldo puede ser usado para cualquiera de los 3 tipos de masajes.
    
- La persona además elige una fecha y hora, que será de lunes a viernes entre las 9AM y 9PM. La sesión dura únicamente una hora.
    
- Simularemos que algunos de esos horarios no se encuentran disponibles y no es posible elegirlos.
    
- Si la persona elige usar su cuponera simplemente puede confirmar la solicitud luego de elegir la fecha y hora, más el tipo de sesión. En caso de elegir el pago individual de la sesión, se mostrará un formulario para ingresar datos de pago, donde el precio estará fijo en 30 dólares americanos (sin opción de cambiar moneda ni monto).
    
- En otra sección de la web, el usuario podrá comprar cuponeras, de 4 y 8 sesiones solamente. Allí también se mostrará el formulario de pago. Debe mostrarse también un precio actualizado a 5% de descuento sobre el total de 4 sesiones, y un 10% sobre el total de 8 sesiones. El descuento debe quedar claro a partir de un precio total tachado y mostando el nuevo con su información de descuento correspondiente.
    
- También aparecerá en todo momento, sobre la parte lateral derecha, un widget mostrando el historial de sesiones que ha tomado la persona. Asumiermos que es un cliente recurrente que ha tomado una sesión semanal. En ese historial, muestra el día, el tipo de masaje y el nombre de la masajista que dió atención (inventa esos datos).
    
- Sobre la barra superior, aparecerá el nombre y apellido de la persona, con un mensaje de bienvenida (como "Bienvenido X") además de un link para modificar sus datos personales (aunque en principio será un link falso -no clickeable-).
    
- EL nombre de la casa de masajes será Penelope. Ese nombre deberá aparecer en el centro de la barra superior con un estilo acorde al servicio.
    
- Habrá un pequeño ícono para cambiar el tema de la página de claro a oscuro.
    
- El diseño general y la tipografía debe inspirar calma y ser agradable a la vista.
    
- Las distintas secciones se mostrarán en un layout de pestañas en lugar de barra lateral izquierda. Existirá la pestaña principal de "Reservar", también la de "Mis cuponeras" que corresponden a lo antedicho. También habrá una pestaña de "Mis reservas" donde aparecerán las reservas de la persona. Inicialmente, al igual que el panel antedicho, la persona contará con un número inventado de visitas hechas en el pasado, pero además aparecerán listadas en la parte superior, las nuevas reservas en un estado de "pendiente", con la posibilidad de ser canceladas (pero no reprogramadas). También habrá una pestaña de "Sobre nosotros" con un párrafo donde se descrbirá brevemente algo sobre la companía (La misma se creó en 1988 en Montevideo, Uruguay por un dos hermanas que llegaron desde Argentina, y puedes inventar algo más al respecto que le de cierto aire familiar a la empresa: como que ha nacido a partir de crear un espacio para revitalizar las energías y servir a las personas en la comunidad, etc).
    
- Los datos mencionados (las reservas previas y las nuevas) vivirán en un archivo csv que será nuestra base de datos que utilice el backend. Es decir, no incluiremos en principio una base de datos formal.
    

- La webapp será single page. Es decir, solo existirá una ruta, y las secciones serán componentes que aparecen en ella.
    

Si estás de acuerdo, hasta allí llegan los requerimientos iniciales, para que me des el prompt. Considera lo que hablamos anteriormente sobre alcance, tecnologías, propósito y espacio para corregir o cambiar cosas.

### usar el prompt en Google AI Studio


Build a minimal single-page web application for managing massage appointments for a fictional massage house called "Penelope".

The application is a didactic prototype. Keep the implementation simple and avoid unnecessary complexity. The goal is to have a functional and visually polished first version that can be iterated on later.

##### Language

The entire user-facing web application must be in Spanish.

This includes:

- Navigation
- Buttons
- Labels
- Forms
- Validation messages
- Status messages
- Error messages
- Reservation information
- Package information
- Informational content

Use natural Spanish appropriate for a wellness/massage service in Uruguay.

##### Technology

Use:

- Python with FastAPI for the backend.
- React with Vite for the frontend.
- TypeScript for the React application.
- Use additional libraries only when they provide clear value for this prototype. For example, Axios for API communication and a lightweight CSS solution or Tailwind CSS for styling are acceptable.
- Use SQLite as the local persistence mechanism.
- Do not use an external database server such as PostgreSQL or MySQL.
- Do not implement authentication, authorization, user registration, real payment processing, email notifications, or other production-oriented infrastructure.
- Do not add automated tests in this first version.

Keep the project structure conventional, simple, and easy to understand.

##### Application

The application represents a massage house called "Penelope".

It is a single-page application. There should be only one main route. The different areas of the application should be displayed as sections/tabs within that page rather than as separate routes.

The application should simulate a logged-in recurring customer. No authentication is required.

Use a fictional customer name and fictional historical data.

##### Main navigation

Use a horizontal tab-based layout rather than a left sidebar.

The application should contain these sections:

1. Reservar
2. Mis cuponeras
3. Mis reservas
4. Sobre nosotros

"Reservar" should be the main/default section.

##### Top bar

Create a top navigation/header area.

It should contain:

- On the left: a greeting such as "Bienvenido, [customer name]".
- A small "Modificar mis datos" link near the customer information. It does not need to be functional in this version and should not navigate anywhere.
- In the center: the name "Penelope", styled as the visual identity of the massage house.
- On the right: a small control/icon that allows the user to switch between light and dark themes.

The overall visual identity should communicate calm, relaxation, warmth and well-being.

Use an elegant but simple typography and a pleasant, modern color palette. Avoid an overly sophisticated or corporate design.

##### Reservar

The main section allows the customer to book a massage session.

There are three massage types:

- RELAJANTE
- DESCONTRACTURANTE
- HÍBRIDA

The customer must select:

- Massage type
- Date
- Time

Available appointments are Monday through Friday, from 9:00 AM to 9:00 PM.

Each appointment lasts exactly one hour.

Simulate unavailable time slots. Some dates/times should appear unavailable and must not be selectable.

Assume the customer currently has a coupon package with 8 available sessions.

The coupon balance can be used for any of the three massage types.

The customer must be able to choose between:

1. Using a session from the coupon package.
2. Paying individually for the selected session.

If the customer chooses to use the coupon package, they can confirm the reservation after selecting the massage type, date and time.

If the customer chooses individual payment, display a payment form before confirming the reservation.

The individual massage price is fixed at USD 30.

Do not provide currency or price customization.

The payment form is only a simulation. Do not process real payments or connect to a payment provider.

After a successful booking, the new reservation should appear as a pending reservation in "Mis reservas".

##### Mis cuponeras

Create a section where the customer can purchase coupon packages.

There are only two packages:

- 4 sessions
- 8 sessions

Use the individual massage price of USD 30 as the basis for calculating the package prices.

Apply these discounts:

- 4-session package: 5% discount over the regular total.
- 8-session package: 10% discount over the regular total.

Make the discount visually explicit.

For example, show:

- The original total price crossed out.
- The discounted price prominently displayed.
- The discount percentage clearly indicated.

Each package should have an option to purchase it.

When the customer chooses to purchase a package, display the same type of simulated payment form used for individual sessions.

Do not implement real payment processing.

##### Mis reservas

Create a section displaying the customer's reservations.

The customer should have fictional historical visits already recorded.

Historical reservations should include information such as:

- Date
- Massage type
- Massage therapist

Invent realistic names for the massage therapists.

Additionally, newly created reservations should appear prominently at the top of the section with a "Pendiente" status.

Pending reservations must have an option to cancel them.

They must NOT have an option to reschedule them.

Cancellation should update the application state and the SQLite-backed data accordingly.

##### Right-side session history widget

On the right side of the application, display a persistent widget showing the customer's previous massage sessions.

Assume the customer is a recurring customer who has historically attended approximately one session per week.

Display fictional historical information including:

- Date
- Massage type
- Massage therapist

This should remain visually accessible while navigating between the main sections.

##### Sobre nosotros

Create an "Sobre nosotros" section with a short, warm description of the massage house.

Use the following fictional background:

Penelope was founded in 1988 in Montevideo, Uruguay, by two sisters who arrived from Argentina.

You may invent additional details that reinforce the idea of a family-oriented business created to provide a welcoming space where people can relax, revitalize their energy and feel cared for as part of the local community.

Keep this section short and appropriate for the prototype.

##### Data persistence

Use SQLite as the local persistence mechanism.

Do not use an external database server such as PostgreSQL or MySQL.

The SQLite database should contain the data needed for:

- Historical reservations
- New reservations created by the user
- Coupon/package information if persistence is needed

The backend should expose simple FastAPI endpoints needed by the frontend to:

- Retrieve the customer's reservations/history.
- Retrieve available appointment information.
- Create a new reservation.
- Cancel a pending reservation.
- Retrieve coupon/package information if needed.

Keep the API simple.

The application does not need to support multiple users. Assume there is only one fictional customer.

Keep the database implementation simple and appropriate for a small prototype.

##### General UX

The application should feel like a coherent massage/wellness service rather than an administrative dashboard.

Prioritize:

- Calm visual design
- Clear hierarchy
- Good spacing
- Simple interactions
- Responsive layout
- Clear feedback after actions

Avoid unnecessary animations, complex navigation, or excessive UI elements.

##### Scope

This is the first version of the application.

Prioritize a working end-to-end prototype over architectural sophistication.

Do not add features that were not requested.

Do not implement authentication, real payments, production databases, email, notifications, automated tests, Docker, CI/CD, or deployment-specific configuration.

The application should be easy to run locally with a FastAPI backend and a Vite/React frontend.

Generate the complete project structure and the initial implementation needed to run and demonstrate the application.
